## D1 — The LLM plans and explains; code computes every number

- **Decision:** The LLM produces (1) a query plan and (2) a narrative explanation of results. Scores, ranks and percentages come only from deterministic Python.
- **Why:** Every number stays auditable and reproducible, which is the point of the scoring requirement. It also defeats prompt injection aimed at numbers.
- **Rejected:** Letting the LLM read raw data and compute or estimate answers.

## D2 — Plan → execute → explain, not a free-form tool loop

- **Decision:** Each turn makes two LLM calls: a planner that returns `QueryPlan`, and an explainer that returns `Explanation`. One deterministic executor runs in between.
- **Why:**
  - Every target question maps to one operation (rank, compare, stat, explain, outlook).
  - A single plan can be evaluated field by field.
  - Two calls fit Groq's 8K tokens/min.
  - No looping or tool-argument drift.
- **Trade-off:** Compound questions are served by the richer operation; for example, *compare* already includes per-hazard breakdowns.

## D3 — Flat, strict JSON schemas + local validation + grounding check

- **Decision:**
  - Schemas are flat. Every field is required, and fields that may not apply are nullable; `additionalProperties: false`.
  - Output is always validated with Pydantic, whatever the provider guarantees. On failure: one retry with the errors, then a clear error answer.
  - Every number in the explanation must appear in the computed result or in the question. Otherwise: retry once, then use a deterministic template.
- **Why:** This shape is what Groq's strict mode requires, and Gemini accepts it too, so the fallback needs no second schema. The grounding check enforces D1 on the narrative.

## D4 — Assumptions, uncertainty, sources and time window are generated by code

- **Decision:** The answer assembler builds these four sections from the plan, the result and `source_status`, not from the LLM.
- **Why:** They are present in every answer by construction, not because a prompt asked for them.

## D5 — Groq `openai/gpt-oss-20b`, Gemini fallback, pinned LiteLLM

- **Decision:** All LLM calls go through LiteLLM. Primary model: Groq `openai/gpt-oss-20b` (strict JSON-schema decoding). Fallback: Gemini on 429, 5xx or timeout. Model IDs come from env.
- **Why:** Strict decoding cuts invalid output. The fallback absorbs Groq's free-tier limit (8K tokens/min).
- **Security:** LiteLLM 1.82.7 and 1.82.8 were malicious PyPI releases (2026-03-24). We exclude them and pin a reviewed version with hashes in `uv.lock`.

## D6 — Four public sources, each with one job

| Source | Job |
|---|---|
| Open-Meteo archive (ERA5) | Observed weather: 10-year climatology and "% of days" stats |
| Open-Meteo forecast + NWS active alerts | Near-term (7-day) risk |
| FEMA National Risk Index | Modeled hazard loss per county |
| OpenFEMA declarations | Realized disaster history per county |

- **Not used:**
  - NOAA ACIS station data (user decision: Open-Meteo only; the reanalysis caveat is stated instead).
  - NWS for history (it keeps only 7 days of alerts).

## D7 — NRI building loss rate → our own national percentile

- **Decision:** Use `{HAZARD}_ALRB` (expected annual building loss rate) and rank it against all 3,232 US counties ourselves. Null means "hazard not applicable" and scores 0.
- **Why:**
  - `RISK_SCORE` is 95–100 for every metro hub (Denver 95.2, Cook 99.97, Dallas 99.65), because it scales with the dollar value exposed in the county. It cannot rank hubs.
  - The composite `*_ALR_NPCTL` includes agriculture. Miami's cold-wave percentile is 91 because of crop freezes, while its building loss rate is about 1.7e-6.
  - A building loss rate measures how hazardous the place is for a facility, independent of county size.
- **Note:** Flood uses `IFLD` (Inland Flooding, which replaced Riverine) and `CFLD` (Coastal). NRI version: December 2025.

## D8 — FEMA: major disasters only, weather types only

- **Decision:** Count DR (major disaster) declarations since 2000 for the hub's county, keep weather incident types only, and de-duplicate by disaster number. This lens gets the lowest weight (0.2).
- **Why:** Raw records mix in COVID (Biological), Fire, and EM declarations (often issued before landfall). Declarations also reflect population and politics, not only the hazard.

## D9 — 10-year observation window (2016–2025)

- **Decision:** Ten full calendar years of daily data per hub, cached forever, pulled at a paced rate once, and shipped as a seed snapshot.
- **Why:** Open-Meteo counts more than 2 weeks of data as several calls. One hub's 10 years ≈ 261 calls, and all 15 ≈ 3,900. Thirty-year normals (~11,700 calls) exceed the 10k/day free cap.
- **Trade-off:** Rare events such as heavy snow are noisier over 10 years. The NRI and FEMA lenses add long-record evidence.

## D10 — Two scores: long-term exposure and near-term risk

- **Decision:**
  - **Exposure** (for investment): long-term, 5 hazard families, mean-based.
  - **Near-term risk** (for alerts): next 7 days, forecast + NWS alerts, max-based.
- **Why:** Investment cares about chronic exposure across hazards. Operations care about the worst hazard this week. Mixing the two would blur both.

## D11 — Fixed-anchor normalization, not min-max

- **Decision:** Each indicator maps to 0–100 through documented anchors (e.g. 25 snow days/yr = 100), capped.
- **Why:** A hub's score doesn't move when other hubs are added or removed, so a score change always means a data change. That is what makes alerts meaningful.
- **Rejected:** Min-max or rank scaling across the roster.

## D12 — Overall exposure = equal-weight mean of families

- **Decision:** Overall = mean of winter, hurricane, flood, severe storm and heat (user decision). Weights can be overridden per question.
- **Why:** It's the most neutral default without the company's own loss data.
- **Trade-off:** A hub with one extreme hazard (Miami/hurricane) is diluted. To compensate, answers always show each hub's top hazard, and hazard-specific questions rank by family.
- **Rejected:** A "mean + worst hazard" blend, and judgment-based disruption weights.

## D13 — Stat thresholds in config, always printed

- **Decision:** "Snowfall day" means ≥ 0.25 cm (the NWS "measurable" 0.1 in). Every stat answer also shows a sensitivity row.
- **Why:** For Denver 2025 the threshold swings the answer from 2.7% to 12.1%:

  | Threshold | Days | % of 2025 |
  |---|---|---|
  | Any snow > 0 | 44 | 12.1% |
  | ≥ 0.25 cm (measurable) | 31 | 8.5% |
  | ≥ 1 cm | 18 | 4.9% |
  | ≥ 2.5 cm (1 in) | 10 | 2.7% |

  Reanalysis also differs from the station (26 measurable-snow days at Denver airport).

## D14 — SQLite + committed seed snapshot

- **Decision:** One SQLite file (WAL mode, stdlib `sqlite3`, no ORM). Real API responses are recorded once into `data/seed/` and used for tests, offline eval and first-run seeding.
- **Why:**
  - The data is tiny (~55k daily rows).
  - It needs date-range queries and atomic writes for scores, alerts and conversations.
  - Zero ops, and easy to inspect.
  - With the seed, a fresh install works without a paced 15-minute download.
- **Rejected:**
  - Postgres: no concurrency need. It's the migration path for multi-instance.
  - JSON files: no range queries or transactions.
  - DuckDB: built for analytics, not small transactional writes.

## D15 — One run script; Docker optional; no cloud deploy yet

- **Decision:** `uv run python scripts/run.py` starts FastAPI (:8000) and Streamlit (:8501) together and stops both together. The Dockerfile runs the same script. There is no Makefile. The cloud host will be chosen later (user decision).
- **Why:** One obvious way to run the app, with or without Docker. Env-only config keeps it deployable to any container host later.

## D16 — Eval: offline by default, `--live` for the real LLM

- **Decision:** 22 cases built around the four example questions, including follow-ups and guardrails.
  - **Offline:** feeds each case's expected plan to the executor and uses the template explainer on seed data. No keys, no network.
  - **`--live`:** runs the real planner and explainer on the same seed data.
- **Why:** Offline checks the deterministic core and the answer contract on every run. Live measures plan accuracy and grounding. Pinning the data keeps expected numbers stable.

## D17 — Pragmatic TDD for core logic

- **Decision:** Core logic (scoring, stats, plan validation, grounding check, executor, assembler, alert diff) is written test-first, with hand-computed fixtures. I/O glue is tested alongside, with every external call mocked.
- **Why:** The numbers are the product, so they get the strongest guarantees. Test-first on glue code would add little.

## D18 — Identity-lite auth

- **Decision:** An allow-listed email gets a signed bearer token with an `analyst` or `admin` role. Ingest and alert runs are admin-only. Built after the core works.
- **Why:** This is the light auth the brief asks for.
- **Limitation (documented):** There is no password or magic link. This is not production authentication.

## D19 — Hub roster is an assumption

- **Decision:** 15 hubs, each placed at its metro's main airport logistics zone, with the county looked up once via the FCC Area API:
  - Midwest (US Census definition): Chicago, Indianapolis, Columbus, Detroit, Minneapolis–St Paul, Kansas City, St. Louis
  - Named in the brief: Denver, Dallas, Houston, Miami
  - Others: Atlanta, Memphis, Newark, Los Angeles
- **Why:** The brief gives no facility list. The roster covers the example questions, and Los Angeles serves as a low-exposure control. It lives in `config/hubs.yaml` and can be replaced.
